# What the last 48 hours established (2026-11-01 -> 2026-11-03)

This is the consolidated record of the HackiOS work on the OnePlus 9 Pro (`lemonadep`, SM8350). It exists
because the same ground kept being re-covered: the GPU story, the 120 Hz question, the two "broken app"
symptoms and the charger were each investigated more than once. Everything below is measured on the phone
unless it is explicitly marked as a reading of the sources. Where a claim was later corrected, the
correction is here and the older note is marked stale.

Read this first, then [`GRAPHICS-STATE-2026-11-03.md`](GRAPHICS-STATE-2026-11-03.md) for the frame-cadence
work and [`NEWER-IOS-AND-CHARGING.md`](NEWER-IOS-AND-CHARGING.md) for the iOS 18/26 research and the
charger's measurements.

## 1. What works right now (verified on the phone)

Standalone image (`boot_b` = UEFI + XNULoader + kernel + `root.apfs`; the iOS system image is read from
`userdata`):

| Works | Notes |
| --- | --- |
| Boot without a computer | Mu-Silicium UEFI for lemonadep, XNULoader, kernel; iOS 16.5 userland |
| Display, GPU | Adreno 660 through **Mesa GL** (`GL=1` build), `metal=2` split, blur/transparency/animation |
| Refresh | panel at 120 Hz with the vsync-period fix and `fb_hz=120`; user reported "smoother, no tearing" |
| Touch, keys, battery UI, backlight | Synaptics S3908, PMK8350/PM8350, BQ28Z610 gauge, DCS 0x51 brightness |
| Wi-Fi | QCA6490 via Linux `ath11k` over PCIe; joins at boot, DHCP by iOS |
| Safari, Location | with `DENY_EXTRA=com.apple.apsd`; Wi-Fi positioning |
| `/private/var` persistence | saved to `userdata` and restored at boot |

Not working, with the cause as far as it is known:

| Broken | Cause (measured) |
| --- | --- |
| Sound | DSP starts, no speaker route; postmarketOS lists audio as broken on this phone under Linux too |
| Weather numbers | Mescal/FairPlay signature fails (`code=12`); the app's internal local-server environment is now reachable but the app sends no request yet (§4) |
| Maps tiles | tile host answers **403** to unsigned requests; Maps itself draws fine (§5) |
| Charging from a charger | MP2650 never acknowledges on I²C (§6) |
| Bluetooth, cellular, camera | not started |
| Power-button shutdown | does not persist `/var`; use the five-finger hold or iOS's own power off |

## 2. GPU: the split that actually works, and what it is not

The Metal driver work (upstream `hakios-metal` plus this tree's AIR translation, patches 1007+) got as far as
`metal80-88`: **the window server draws on the GPU with zero refused calls and zero hangs**, and `metal89-90`
fixed the teardown panic. What it does not do yet is put iOS's UI on the panel through Metal.

What is verified and in use is the OpenGL ES path with a deliberate split:

* `metal=3` showed the Metal device to **every** process, including `backboardd`. The window server cannot
  run on Metal here (`metallib_url` load fails), so it printed "Failed to initialize Metal or OpenGLES
  contexts" and fell back to the **software renderer**: no blur, no transparency, wrong colours.
* `metal=2` is the "sandwich": applications get a Metal device, `backboardd` keeps OpenGL ES. Log proof:
  `redwood: metal: no device in this process; CoreAnimation keeps OpenGL ES by itself` together with
  `accelerated renderer (0x...)` and **zero** "Software renderer" lines.
* The image must also be built with `GL=1`, or there is no GL stack to fall back to. That was the second,
  independent cause of the same symptom: the image was 18.6 MB (`root.apfs`) instead of 25.3 MB, with no
  `libredwood-gl.dylib` and no Mesa. With it, `root.apfs` is ~25.1-25.3 MB and GL works.

Trap for the next person: `USERLAND_VARS="GL=1 ..."` is a variable of the upstream wrapper
(`common/build.sh`); passing it to `userland/build.sh` directly does nothing. Export `GL=1 ADSP=1 ...`
yourself or the image silently comes out without Mesa (18.6 MB is the tell).

## 3. 120 Hz: what was changed, and what the numbers did not show

* `MiniIOMobileFramebuffer.cpp` defaults `kFBRefreshHz` to 60; `fb_hz=120` sets it at boot.
* `IOMobileFramebufferUserClient::vsync()` sent CoreAnimation `now` in the slot CA reads as the refresh
  **period**, so CA's next deadline came out as roughly `now + now`. `tools/fix-vsync-period.py` fixes it,
  and the patched file is in the kernel build tree.
* Kernel was rebuilt in a fresh tree (`/root/fkernel/xnu-fresh/xnu-8796.121.2`), `fb_hz=120` in the payload.

Measured, 200 s runs each:

| | `frames1.log` (60 Hz, no period fix) | `cadence120.log` (period fix + `fb_hz=120`) |
| --- | --- | --- |
| frames drawn in 200 s | 3060 | 3220 |
| CPU per frame | 3566 us | 3836 us |
| GL errors | 0 | 0 |

**The counters did not show a frame-rate gain**, and that is not evidence the patch is wrong: these count
how often CoreAnimation *draws*, which is the applications' own redraw rate, not the panel's refresh. The
honest summary is: the patch is in, the panel is at 120 Hz, the user perceives it as smoother and tear-free,
and a vsync-delivery counter is still the missing measurement.

## 4. Weather: from "FairPlay is impossible" to "we reach the local server, the app still sends nothing"

The chain, measured on 2026-11-01:

```
AMSMescalFairPlay: Init failed ... code=12 "Mescal Failed" / "Failed to fetch hardware info"
  -> [WeatherDataService] Error while creating local signature
    -> the request is never sent (so the digits stay blank)
```

An unsigned `net_test fetch` of the same endpoint answers **401**, so Apple would refuse it anyway. A kernel
FairPlay stub was considered and dropped: `fairplayd` never calls IOKit (three runs, zero
`IOServiceMatching`/`IOServiceOpen`), so a kernel stub cannot help.

What changed the picture was reading WeatherCore out of the dyld shared cache (it has no code on the
volume; the cache is at `ios165/20F66__iPhone10,3_6/dyld_shared_cache_arm64*`). Its own configuration
carries an environment called **"Local - Mock Server"** whose data endpoint is plain
`http://localhost:5033`, selected by defaults keys that sit together in one string table:

```
weather.environment.contentEnvironment      values: "Production - Origin" / "Local - Mock Server"
weather.environment.localServerURL          literal beside them: "http://localhost"
weather.environment.localServerPort
weather.environment.aps
```

That is why `localhost:5033` appears nowhere as a whole string in the app binary: the URL and the port are
two keys, and the selector is a defaults value.

Built for this (experimental image only): `src/inject_weather.c` -> `/redwood/lib/libredwood-weather.dylib`,
injected into `Weather`, `WeatherWidget` and `weatherd`; a constructor sets the keys, and a thread listens on
`127.0.0.1:5033`, logging every request line/header and answering `/var/mobile/redwood-weather.json` or `{}`.
Also added `open_demand()` to the SpringBoard library: it opens the bundle id in
`/var/mobile/redwood-open` 25/45/65 s after SpringBoard starts, because nothing in this port can launch an
app without a finger on the screen. (It reports `refused` from `-[LSApplicationWorkspace
openApplicationWithBundleID:]` while FrontBoard spawns the app anyway — the return value is not the answer.)

Result of run `weathershim3` (250 s, `metal=2`, `fb_hz=120`, GL drawing, 574 KB log, no faults): the library
loaded in Weather, all three keys were set, the server listened — and **the app made zero requests**,
logged nothing of its own, and spawned neither `weatherd` nor `WeatherWidget`. It did reach the foreground
(`<sceneID:com.apple.weather-default> unspecified -> foreground`, 14:10:45) with ~3 minutes of log after it.

So, unlike 1 November, there is no Mescal error either. Two readings, and one boot separates them:

1. the environment *was* taken and the endpoint is built from the keys in a shape the framework rejects
   (`localServerURL` may want the port inside it, or the keys are read from a domain other than the one the
   constructor writes), so no request is made; or
2. `contentEnvironment` wants a raw value, not the display name: the shipped JSON spells the others
   `"PRODUCTION"`/`"STAGING"`, while the literals beside the keys are `"Production - Origin"` and
   `"Local - Mock Server"`.

The experiment that decides it: boot with `contentEnvironment` **unset** while the server still serves 5033
and see whether the Mescal error returns. The shim as it ran and as it is committed
([`weather/inject_weather.c`](weather/inject_weather.c), syntax-checked, 221 lines) sets all three keys
unconditionally, so that experiment needs one line removed and a rebuild. A variant that takes the value from
`/var/mobile/redwood-weather-env` and logs every `weather.*` defaults read (by watching `-objectForKey:`) was
drafted but its patch did not land — treat it as not existing until it is in the file and compiled. That
watcher is worth adding first, because it answers "does the framework ask for those keys at all?" in the same
boot as the unset test.

> Stale note: earlier text in this repository said the Local environment selector had to be found "in the
> cache or by interposing on the config object". The keys are known now; only their serialization is open.

## 5. Maps: not Metal, not the GPU — a 403

`Maps` launches, logs `Maps application main() started`, reaches the foreground, and draws its own chrome
(search field, controls). There is not one Metal/renderer complaint attributed to it. A missing Metal device
looks different here: earlier `metal=1` runs printed `metal_test: the context's Metal device: nil` and the
process could not open a context at all.

The data never arrives. Measured from the phone with `net_test fetch` in the same session:

| Request | Answer |
| --- | --- |
| `gspe19-ssl.ls.apple.com` (tiles) | **403, 0 bytes** |
| `bag.itunes.apple.com/bag.xml` (control) | **200**, `x-set-apple-store-front: 143500-2,8` |
| `weather-data.apple.com/v3/...` | **401**, 25 bytes |

Tile requests are GeoServices-signed the way weather is Mescal-signed. So: a working Metal context with
nothing to draw. The fix, if any, is a different tile source behind a patched `GeoServices` — much bigger
than Weather, because Apple's vector tiles have no keyless public equivalent.

## 6. Charging: the charger chip never answers

Every boot prints the same line:

```
battery: gauge ok: 94%, 8443 mV, -297 mA ... charger NOT ANSWERING: status 0xff faults 0xff,
in 0 mV 0 mA, charging 0 mA, battery 0 mV; 0+22 reads not acknowledged, 0+0 clock waits too long
```

The BQ28Z610 gauge answers; the **MP2650** charger does not acknowledge on I²C at all (`0xff` status is an
unanswered bus, not a fault code). `adsp=1` also wants `fw-audio/adsp.mdt`, and `fw-audio` is absent from this
machine, so the DSP that owns charging on this platform is not in the image either. Pulling those files from
the phone's `modem_a` is the next concrete step; until then the phone charges only when it is off, on a wall
charger, with the panel dark.

Logistics that cost time, so they are written down:

* TWRP charging with both backlights at 0 is not useful: `usb/current_now` 500 mA but `battery/current_now`
  only ~-88 mA, capacity flat, then shutdown.
* Do not use a USB port on a computer as the charger.

## 7. How the device was driven hands-free (and how to repeat it)

Nothing was flashed during this work; the phone boots RAM payloads over USB:

```
fastboot boot out/hackios/lemonadep-boot.img      # Mu-Silicium UEFI -> XNULoader
# then, per iteration and with the loader session kept:
fastboot stage system.apfs                        # once per loader boot (~90 s, 2.5 GB)
fastboot stage run-payload.bin                    # kernel + root.apfs + boot-args
fastboot oem run
fastboot oem log; fastboot get_staged <log>.raw    # live and final capture
```

Helpers in this directory:

| Script | What it does |
| --- | --- |
| `usb-test.sh LOGNAME [SECS]` | the whole iteration: finds or boots the loader, stages the image once, stages and runs the payload, fetches live logs at +60/+120 s and the final log, then leaves the loader up. Bounded at every step |
| `repack-payload.sh` | repacks **only** `run-payload.bin` from the current `userland/root.apfs` plus `lemonadep.conf`'s boot-args (`SECS=` bounds the run) |
| `metal-cycle.sh`, `metal-run.sh`, `metal-rerun.sh` | the earlier Metal-specific loops |

Boot arguments that matter (in `common/devices/lemonadep.conf`): `metal=2` (the split), `gpu=1`, `GL=1` in
the userland build, `fb_hz=120`, `fbwidth=1242 fbheight=2688` (iPhone XS Max layout, scaled to the panel),
`sweetwlan=17 wlan_ath=1 wifi_join=1`, `battery=1 backlight=1 adsp=1`, `DENY_EXTRA=com.apple.apsd`,
`ALLOW=locationd LOCATION_ON=1`.

## 8. Kernel build: the real break, and the reliable way to build

The recurring `config_all`/`Private.symbolset` failure at the end of a build is **noise** — the kernel binary
is already there. The break that actually stopped builds was at **link** time: `lemonadep_logkeep_init`,
`lemonadep_logkeep_return`, `lemonadep_wlan_init` and `lemonadep_wlan_reserve` are called from
`redwood_input.c`/`loader_return` and live in `bsd/dev/lemonadep_logkeep.c` and `bsd/dev/lemonadep_wlan.c`.
Those files ship in `xnu/files/`, but the three lines that compile them existed only in the working tree's
`bsd/conf/files`, never in the overlay. Copying the old `bsd/conf/files` into `xnu/files/bsd/conf/files`
fixes every fresh tree.

```
bash xnu/apply.sh /root/fkernel/xnu-fresh/xnu-8796.121.2
XNU_SRC=/root/fkernel/xnu-fresh/xnu-8796.121.2 bash xnu-build.sh -j6 -k
```

`~/fkernel/mach.nov3.bak` is the kernel from before the 120 Hz change; `~/fkernel/root.apfs.good.bak` is the
known-good root image. Restoring those two returns the phone to the state verified on 2026-11-03 04:44.

## 9. Reading iOS internals without a jailbreak

Two techniques were what actually moved things forward, and both are reusable:

* **The dyld shared cache is the source for framework code.** On this image the frameworks are code-less on
  the volume (`WeatherCore.framework` has only plists); the code is in
  `ios165/20F66__iPhone10,3_6/dyld_shared_cache_arm64*` (43 files). `strings -a` plus `dd` around a match is
  enough to recover configuration tables, defaults keys and even the full JSON `AppConfiguration`.
* **A library inside the process beats guessing from outside.** `etc/inject.conf` = `LIBRARY NAME...` per
  line, handed to `kern.exec_inject` at boot; the library's constructor runs before the app's `main`. That
  is how the defaults were set and the local server started, and it is the mechanism to use for any further
  in-process experiment. Note that a *file* cannot launch an app here — that is why `open_demand()` exists in
  the SpringBoard library.

## 10. Newer iOS, in one paragraph

iOS 16.5 is no longer the ceiling elsewhere: Bergamota boots the unmodified **iOS 18.7.8** userland of an
iPhone XR on a Poco F1 with xnu-11215, by rewriting every arm64e Mach-O *and the dyld shared cache* in place
(`RETAA`->`RET`, `BRAA`->`BR`, `PACIA`->`NOP`) and re-signing ad hoc. iOS 17 has no public Android port;
iOS 26 runs only in QEMU. The full sourcing is in [`NEWER-IOS-AND-CHARGING.md`](NEWER-IOS-AND-CHARGING.md).
For this phone the transferable piece is the PAC rewrite of a userland image, not the kernel.

## 11. If we ported Linux (Luma, Armada, postmarketOS) — what these findings are worth

Short answer: the boot chain and half the hardware map are already done, and that is the expensive half of a
Linux port; what is missing is a mainline device tree and a GPU stack, and those are not what this port
produced.

What transfers directly:

* **A working UEFI on this exact phone.** Mu-Silicium's lemonadep FD boots, takes USB commands and hands off
  to a payload. Armada explicitly boots through an EFI path (`systemd-boot` + `dtbloader`, with a deprecated
  `/KERNEL` for older ABLs); postmarketOS and most mainline ports use the same UEFI or a `boot.img` path.
  Our `fastboot boot` recipe, the A/B slot facts, `os_version`/`os_patch_level` and the loader's limits are
  all measured (`BOOT_lemonadep.md`).
* **Display facts that are usually the first wall.** ABL leaves the DSI command-mode panel (Samsung
  AMB670YF01, 1080x2412) with autorefresh on and a splash plane at `0xE4D00000`; the panel needs no geometry
  fix; 120 Hz works once the vsync period is right. A Linux port still needs a proper `msm`/DPU + panel
  driver, but the timings and the "who initialised what" question are answered.
* **Input.** Touch is Synaptics S3908 over TCM v1/v2 on GENI SE4 (bit-banged I²C on gpio20/21 because SE4 is
  GSI-only for us), keys are PMK8350 PON + PM8350 GPIO6. Under Linux these are `syna,rmi`/TCM and
  `pm8941-pwrkey`-style drivers; the addresses, GPIOs and protocol version are already in
  `HWMAP_lemonadep.md`.
* **Wi-Fi.** This port runs Linux's own `ath11k` against the QCA6490 over PCIe, including firmware
  (`amss.bin`, `m3.bin`, `bdwlan.bin`, `regdb.bin`) pulled from the phone, the DMA pool reservation and the
  board-data path. That is the same driver a Linux port would use; the firmware extraction and the
  "reserve 64 MB of DMA before the GPU" lesson transfer as-is.
* **Power.** Real gauge readings (BQ28Z610 over I²C), the DCS 0x51 backlight command, and the MP2650 finding:
  the charger is not on the I²C bus as we drive it and charging is owned by the ADSP, which needs
  `fw-audio` from `modem_a`. A Linux port hits the same chip; knowing it does not ACK saves a week.

What does **not** transfer, and is the actual work:

* A mainline **device tree** for SM8350/lemonadep (postmarketOS has a port with a known bug: it does not even
  bring up USB networking on 2026-04 builds), plus panel, touch, UFS and regulator plumbing in mainline.
* A **GPU stack**: mainline `msm`/Adreno + Mesa **Turnip** for Vulkan. Our GL path is a Redwood-specific
  Mesa build against a custom kernel GPU service, so it is not reusable; the GMU/SMMU knowledge (registers,
  firmware layout, `dma-coherent`, stream `<5 0x400>`) is.
* For **Armada** specifically: it is a SteamOS-like Fedora `bootc` image for ARM **handhelds**, supporting a
  fixed device list (ROCKNIX-derived). Adding lemonadep means a new device in that list *and* a mainline
  kernel with working KMS, Vulkan and input — gamescope/Steam with FEX/Proton on an Adreno 660 is a
  performance question on its own. Nothing in this repository makes that device entry exist.
* For **Luma**: it is a GNOME-based, desktop/tablet/phone distribution (a Fedora-based x86_64 nightly today,
  with device ports appearing for ARM phones). Same requirement: a bootable mainline kernel for this SoC.

So the honest answer: yes, this work de-risks a Linux port substantially — UEFI, panel, touch, keys, Wi-Fi
firmware and the charger's real behaviour are all measured here, and they are exactly the pieces that
usually take months. But neither Luma nor Armada is "installable" from what we have; both need an SM8350
mainline device tree with display and input, and Armada additionally needs a Vulkan-capable GPU stack. The
realistic order is: (1) get postmarketOS/mainline booting here with USB networking, (2) display + touch in
mainline, (3) Turnip/Vulkan, (4) then talk about a gaming image. Step (1) is where our UEFI payload and
`usb-test.sh` loop would pay off immediately.

## 12. Open questions, in the order they should be answered

1. Weather: does `contentEnvironment` want the display name or a raw value? One boot with the key unset
   decides it (§4), and the shim already logs which keys are read.
2. Weather: which paths does the app ask a local server for? The server logs them the moment a request
   arrives; the answer shapes the JSON we have to serve.
3. 120 Hz: a real vsync-delivery counter, to replace the frame-draw counters that cannot show it.
4. Charging: pull `fw-audio` (and the charger's own firmware, if any) from `modem_a` and retry `adsp=1`.
5. Maps: only worth starting once a tile source exists; it is not a renderer bug (§5).
